## 完整提示词

```text
【MemHub 自动化工程暗知识与长效记忆沉淀】
你的任务是全面复盘当前会话，榨取出可供团队跨项目、跨会话长期复用的【高密度工程硬核知识】。
必须是对未来的系统演进、线上排错、业务迭代具有确凿指导价值的干货！
若本会话仅为临时性任务进度、简单查询、日常答疑或未定位根因的尝试，直接回复 "无需沉淀"，绝对禁止存入无长期复用价值的流水账！

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
一、先盘点产出物，再动手写卡（关键步骤，不可跳过）：
第一步：通读整个会话，回答一个问题——"这次会话整体上完成了哪些有沉淀价值的产出物？"
   - 产出物 = 本次任务产生的一块独立结论/方案/决策/事实知识，不是零散的技术细节。
   - 分析评估类：产出物是分析结论（影响面、知识梳理、现状澄清）；
   - 设计开发类：产出物是方案与实现（选型决策、代码改法）；
   - 排错类：产出物是根因与治本方案。
第二步：把产出物列成清单，逐项判断是否值得单独成卡（有长期复用价值 = 值得）。
第三步：每块独立产出物各出一张卡；既不要把多块产出物硬塞进一张卡，也不要只抓其中一块局部细节而漏掉主干。
   反例：一个"评估数据库升级影响"的会话，只抽了其中一句"某处 SQL 会报错"，却漏掉了"库归属/影响面/升级路线"这三块主干结论，即为严重跑偏。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
二、正文撰写规范（固定五段式，简洁优先，能一句话说清的绝不用两句）：
正文必须按以下五段组织（使用这五段作为小标题）：
1. 【目标】：做了什么、任务目标是什么；有多个目标就写多条，并说明是否都已达成。
2. 【背景】：了解到的背景，即“现状 -> 目标”，包括业务事实、业务逻辑、技术架构等。
3. 【方案】：为达成目标采用的方案是什么。【非必填】——查询、分析类等非设计实现的任务可省略此段。
4. 【结论】：从本次任务中总结出的关键信息与最终结论（梳理出的事实、判定的结果等）。
5. 【经验】：有什么坑或问题需要告知其他人。【有才写，没有就整段不写，严禁硬凑】。
补充铁律：
- 语言极简，一个短句讲一个事实，不复述过程；每句话都要携带可复用的具体结论（实体名/判据/正解）。
- 严禁写排查流水账与一次性细节（逐步排查时间线、具体设备号/时间点/人员对话、环境偶发状态）。
- 证据从简，只保留结论性关键证据（一行关键报错、一条核心判据、关键代码/配置片段），不堆砌大段日志。
- 严禁出现“标准环境”、“结合业务评估”等敷衍废话。

三、标题规格（必须是 20-40 字的一句话技术暗知识指纹）：
格式固定为：[业务模块/核心技术] 触发诱因或场景 -> 架构结论或正解 (严禁句号，直奔主题)
❌ 错误反例: [ProductService/多语言] 硬编码大写Default查utf8mb4_bin库致Banner图片URL全空 -> 统一小写default(Constants.DEFAULT_LANGUAGE) (103字，把正文堆进标题)
✅ 正确标杆: [ProductService/多语言] 排序规则utf8mb4_bin致素材URL为空 -> 统一小写default常量 (43字，干脆利落)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
四、落盘保存规约：
1. 若具备沉淀价值，必须调用 memhub_save 工具进行保存，参数规范：
   - title: [模块/技术] 诱因 -> 结论 (20-40字)
   - category: 固定填 "default"（本版不做分类判定）
   - tags: [核心技术标签1, 业务模块标签2]
   - content: 按【目标】【背景】【方案】【结论】【经验】五段式撰写的简洁 Markdown 正文（方案可省，经验无则不写）
   - session_id: "{{SESSION_ID}}"
   - 【所属项目】：必须准确填写 "{{PROJECT}}"！
2. 按第一步盘点出的产出物清单，每块独立产出物各保存一张卡。
```
