# 设计评审裁决报告：OpenCode v1/v2 双版本适配方案 v2（第二轮 · 3 视角评审 + BATTLE）

> 变更编号：2026-09-24_memhub-opencode-v1v2-adapter
> 评审轮次：第二轮（v1 方案 REJECTED → 真机实测 → v2 方案 → 3 视角评审 → BATTLE 互评）
> 评审时间：2026-09-24
> 评审方式：3 个独立 subagent（架构正确性 A / 破坏性与风险 B / 测试充分性 C）分别评审 → 三方 BATTLE 互评 → 主 agent 交叉裁决

## 0. 一句话结论

**REJECTED（不通过）。** 方案 v2 的**修复方向被真机 F1–F15 全数验证为正确**（idle 消息判完成、分页拉全、fork 字段兜底、探测收紧、V2 接受 Basic Auth），但**方案粒度不足以落地**：核心的「完成判定」（§4.2）与「分页」（§4.3）两块设计**在真机上不可用或自相矛盾**，且 BATTLE 中三方独立收敛到同一组核心风险，共识度高。

## 3. 三方评审 → BATTLE → 交叉裁决的收敛过程

### 3.1 三方初评（均 REJECTED）

| 视角 | P0 数 | 核心主张 |
|---|---|---|
| **A 架构正确性** | 3 | 信号1 无落地点 / outcome 未区分失败态 / order+cursor 互斥 |
| **B 破坏性风险** | 2 | V1 分页回归 / 完成判定与超时语义冲突 |
| **C 测试充分性** | 8 | 测试计划零五元组 / 分页不可证伪 / mock 固化错误行为 等 |

### 3.2 BATTLE 后自我校准（这是本轮最有价值的部分）

**三方都主动撤回/修正了自己的问题项，而非互相攻击：**

| 方 | 加严 | 认领遗漏 | 撤回/放松 |
|---|---|---|---|
| **A** | P1-D 升 P0；接受 C 的 §7/§8a 升 P0 | 承认遗漏 **V1 分页回归**、**R8 凭据外发**、**既有测试冲突** | P0-C 措辞「可能失效」→「确定失效」 |
| **B** | P1（asc+cursor）升 P0 | 承认对 failed/interrupted 判断过宽 | **撤回「25 分钟超时级联」**（误读 `daemon.js:234` 默认 `limit=1`，主动认错） |
| **C** | — | — | **8 个 P0 校准为 2 个**（承认「把测试缺口一律喊 P0」的定级膨胀）；**5c 缺口因 F14 关闭** |

**说明**：B 撤回的「25 分钟级联」是一个**编造性推断**（未核实默认值），在 BATTLE 中被自身推翻——这证明 battle 机制有效地过滤了未经核实的断言。

### 3.3 三方最终收敛的三个共识核心

**三个独立视角在 battle 后独立收敛到同一组核心风险：**

1. **分页设计不可落地**（A-P0-C + B-P0-1 + F13）—— 三方一致
2. **完成判定不可落地且内部矛盾**（A-P0-A + A-P1-D + B-P0-2(a) + C-§4）—— 三方一致
3. **失败/超时被误判成功 → 数据丢失**（A-P0-B + B-P0-2(b) + C-R11-2）—— 三方一致

## 4. 最终裁决：P0 合并清单

**主 agent 采用 A 的「同一代码落点 + 同一修复动作 → 合并」原则**（理由：避免 B 的 6 条保守性拆分造成重复计数，也避免 C 的 2 条过粗导致漏项）。最终 = **5 条 P0**。

| # | P0 名称 | 来源 | 位置 | 证据 | 放行要求 |
|---|---|---|---|---|---|
| **P0-1** | §4.3 分页方案**双版本均不可落地** | A-P0-C + B-P0-1 + F13 | `tech-design.md:110-112` | **F13**：`order+cursor` → 400 硬错；翻页只能只带 cursor 且恒 desc。V1 侧：`opencode-client.js:146-151/368` 裸数组无 cursor；`resolveVersion:118` 探测失败**强制兜底 V1** | 改为「只带 cursor 翻页 + 内存取最新」；`readAllMessages` **按 version 分流**（V1 单次裸 GET）；给页数/条数硬上限**具体数值** |
| **P0-2** | §4.2 完成判定**不可落地且内部矛盾**（三合一） | A-P0-A + A-P1-D + B-P0-2(a) + C-§4 | `tech-design.md:95-107` vs `opencode-client.js:623/625/670` | 信号1 无接入点（`:623` 只认 assistant）；改 `unknown`（`:107`）使 `:670` 短路在 V2 **永不成立**；双信号布尔关系未定义，`:625` 为 `\|\| streamed` ⇒ R3 复活 | 明确 idle 判定**接入函数**；`:670` **按版本分流**；明确双信号 **AND/OR** 并删除 `\|\| streamed` |

### 4.1 关于「C 只留 2 条」的裁决说明

C 校准后只保留 2 条「必然致数据丢失」的真 P0，主张其余降为 P1/P2。**主 agent 不采纳此过粗口径**，理由：
- C 将「分页方案被真机证伪」排除在 P0 之外 —— 但 F13 已把 v2 §4.3 的唯一手段判为**确定失效**，这是**方案不可落地**，非「验证缺口」；
- C 将「CI 反固化」降 P1 —— 但 **F15 证明 mock 会反向固化 bug**（若有人为让 CI 绿而改回旧语义），属**产品缺陷固化**，非单纯验证缺口；
- C 自述「2 条」与其正文实际列出的 3 条**自相矛盾**。

### 4.2 关于「B 的 6 条」的裁决说明

B 将「超时即 EXTRACTED」（P0-3）与「failed/interrupted 未区分」（P0-4）分立。主 agent **合并为 P0-3**，理由：二者落点同为 `daemon.js:468-479` 的**同一布尔判定**、修复动作为**同一处重构**，是同一缺陷的两个观察角，合并后子项全保留、不丢信息。

## 8. 最终裁决

**REJECTED。**

**放行门槛**：P0-1 ~ P0-5 全部修复 + 第 5 节 P1 显式表态 + 第 6 节 T1~T5 测试补齐。

**一句话**：v2 的**方向对、证据硬**，但**设计方案本身在真机上不可落地**（分页 400、完成判定自相矛盾）+ 上层 `daemon.js` 的「超时即成功」会把 V2 必然触发的超时转化为**静默数据丢失**。三者构成闭环风险，故不予放行。
