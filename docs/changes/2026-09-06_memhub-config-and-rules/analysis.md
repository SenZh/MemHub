# 现状分析与方案选型：MemHub

## 1. 事实清单与推断清单

### 事实清单 (Facts)
1. 当前 `package.json` 中的命令绑定了 `"hub": "./src/cli.js"`，与知名开源工具（如 GitHub Hub CLI）存在名字冲突风险；
2. 当前 `src/adapters/opencode.js` 第 36 行硬编码了时间计算：`AND (time_updated < (? - 2 * 60 * 60 * 1000) OR ? = true)`；
3. 当前 `scanCandidateSessions` 仅做了 `parent_id IS NULL` 和标题黑名单过滤，没有针对会话所在工作区路径（`directory` 字段）的包含（include）与排除（exclude）判定；
4. OpenCode 的 `session` 表中的 `directory` 字段记录了会话所属的物理绝对路径（如 `D:/workspace/project-a`）。

### 推断清单 (Inferences)
1. 开发者在日常使用时，可能只想让 MemHub 自动管理特定工作目录（如商业项目），而不希望采集个人实验、临时 demo 或带有敏感代码的目录；
2. 开发者在做密集开发时，可能希望缩短静默判定时间（例如 30 分钟），而挂起长期任务时可能希望延长（例如 4 小时），静态常量无法满足实际工程需要。

## 2. 方案对比表

| 方案 | 描述 | 优点 | 缺点 | 风险 | 验证成本 | 推荐理由 | 不选理由 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **方案 A：硬编码参数扩展** | 仅在 CLI 运行时作为参数传入（如 `mem-hub scan --idle 30 --exclude xxx`），不持久化到配置 | 实现极其简单，无需改动配置文件逻辑 | 自动化定时任务（Cron/后台服务）无法记忆参数，每次都得人工输一长串参数 | 规则易漏填导致误采集 | 低 | — | 无法支撑“用户配置一次、后续自动采集生效”的诉求 |
| **方案 B：两级配置 + 统一过滤引擎（选）** | 在全局/项目级 `config.json` 固化 `idleMinutes` 与 `scanRules`，同时允许 CLI 显式参数动态覆盖；内置轻量 Glob/前缀匹配器 | **最符合工程规范**。开箱即用，支持一次配置全局生效，也支持单次命令临时覆盖，具备 include/exclude 完备规则 | 需要编写轻量安全的路径模式匹配逻辑 | 跨平台路径斜杠（Windows `\` 与 Linux `/`）处理需严谨 | 中 | ✅ **推荐**：既有配置文件兜底，又有动态覆盖能力，完美满足工业级要求 | — |

## 3. 根因剖析与风险控制
- **Windows 路径大小写与反斜杠风险**：在 Windows 环境下，`D:\workspace\proj` 与 `d:/workspace/proj` 是同一路径。路径规则匹配前必须进行统一规范化处理：`path.resolve(p).replace(/\\/g, '/').toLowerCase()`；
- **配置加载性能**：扫描可能涉及数十个候选会话，匹配规则必须在扫描前预编译成正则或模式匹配函数，避免在每次循环中重复解析配置。
